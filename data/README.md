# Data

Scripts and one small synthetic data slice live here. The full IBM files are never committed (see .gitignore).

## aml_slice_hi_small.csv

A small slice of the IBM AML dataset, used for the Monitor (AML alert investigation) module.

- **Size:** about 2.3 MB, 25,493 rows, 522 known laundering transfers (every other row is a normal transfer).
- **Source dataset:** "Transactions for Anti Money Laundering (AML)", HI-Small version.
- **Author:** Erik Altman (IBM).
- **Link:** https://www.kaggle.com/datasets/ealtman2019/ibm-transactions-for-anti-money-laundering-aml
- **License shown on the Kaggle page:** CDLA Sharing 1.0 (Community Data License Agreement, Sharing, version 1.0). Text: https://cdla.dev/sharing-1-0/
- **What the license means for this file:** this slice is a copy of part of the IBM data, so anyone who receives it from this repo gets it under CDLA Sharing 1.0 as well, and the attribution above must stay with it. The code in this repo is not covered by that license.
- **Synthetic:** yes. The dataset is generated by a simulator. It contains no real customers, accounts or transactions.

### How the slice was made

Built in a Kaggle notebook (heavy data work stays out of Codespaces) from the HI-Small transactions file and its laundering patterns file, using a fixed random seed of 42. The steps were:

1. Whole laundering schemes: pick up to 8 complete schemes for each of the 8 scheme families (BIPARTITE, CYCLE, FAN-IN, FAN-OUT, GATHER-SCATTER, RANDOM, SCATTER-GATHER, STACK). "Whole" means every transfer in a chosen scheme is kept, so no pattern is cut in half. Every family reached the limit of 8, giving 64 schemes.
2. Normal transfers on the same accounts: add up to 15,000 normal transfers that touch the accounts in those schemes, so the laundering sits inside realistic account activity.
3. Random normal transfers: add 10,000 random normal transfers, so the slice has a realistic share of unrelated normal activity.
4. Remove duplicate rows.

The result is 25,493 rows, of which 522 are laundering.

Known artifact: normal traffic almost stops after 2022-09-10, while laundering schemes run on to 2022-09-17, so 126 of the 198 transfers dated 11 to 17 September are laundering. Late dates (and late transfer ids, which follow time order) therefore give away the answer. See docs/decisions/0006-late-date-leak.md for how evals handle it.

### Columns

| Column | Meaning |
|---|---|
| ts | When the transfer happened, as `YYYY/MM/DD HH:MM`. Rows run from 2022/09/01 to 2022/09/17 and are sorted by time. |
| from_bank | Numeric id of the bank the money was sent from. |
| from_acct | Hashed id of the sending account. |
| to_bank | Numeric id of the bank the money went to. |
| to_acct | Hashed id of the receiving account. |
| amt_recv | Amount the receiver got, in the currency `cur_recv`. |
| cur_recv | Currency the receiver got (for example US Dollar, Euro). |
| amt_paid | Amount the sender paid, in the currency `cur_paid`. |
| cur_paid | Currency the sender paid. |
| fmt | Payment format: Cheque, Credit Card, ACH, Cash, Reinvestment, Wire or Bitcoin. |
| laundering | The label. 1 means the transfer is part of a known laundering scheme, 0 means normal. |
| attempt_id | Id of the laundering scheme this transfer belongs to. Blank for normal transfers. Stored like `101.0`. |
| attempt_type | Scheme family, one of the 8 listed above. Blank for normal transfers. |

`attempt_id` and `attempt_type` are blank on every normal transfer (all 24,971 of them) and filled on every laundering transfer (all 522).

Notes:
- `amt_recv` and `amt_paid` differ on 604 rows, because the two sides can use different currencies.
- Some rows send money from an account to itself (2,429 rows, mostly the Reinvestment format).
- The `laundering` label is ground truth from the simulator. It is the answer key for evals, never an input to the agent.

### Reproducing

Open the IBM AML dataset on Kaggle, create a notebook with the dataset attached, use the HI-Small files only, and rerun the steps above with seed 42.
