## 1. Purpose

A personal portfolio project with three goals:

1. Learn harness engineering properly: build an agent harness from scratch (loop, tools, verifiers, guardrails, memory, evals, observability) rather than relying on an agent framework.
2. Build real finance domain knowledge (anti-money laundering, business onboarding, credit analysis) by automating the work bank analysts do.
3. Ship a hosted, demoable system with measurable results (accuracy, false-positive reduction, calibration, cost per case) that can be shown to employers.

About the owner: experienced with Python, FastAPI, Next.js and TypeScript, PostgreSQL and SQL, Docker, GitHub Actions, RAG pipelines and production LLM agents with tool use and schema-constrained outputs. New to the finance domain. When a finance concept comes up, explain it briefly in plain terms and add it to docs/glossary.md.

## 2. Scope and build order

Three modules share one harness, one case management UI and one eval runner. Build strictly in this order; each module must be complete and evaluated before the next starts.

### Module 1: Monitor (AML alert investigation)
- Input: alerts generated by a deterministic rules layer over transaction data.
- Agent task: investigate each alert using read-only tools, then decide.
- Output (schema-validated): disposition (close or escalate), suspected typology, confidence score, and a case narrative where every claim cites transaction or account IDs.
- Ground truth: IBM synthetic AML dataset labels (which transactions are laundering, and the pattern each belongs to).
- Why first: it has real labels, so the eval harness can be built and validated properly.

### Module 2: Onboard (KYB, know your business)
- Input: a business applying to become a customer (company name or registration number).
- Agent task: verify the entity, find officers and beneficial owners, screen everyone against sanctions lists, assign a risk rating.
- Output: entity profile, ownership structure, screening results with match scores, risk rating with evidence.
- Ground truth: a hand-built test set of real UK companies (structure checked manually against Companies House) plus seeded test cases where officer names are variants of sanctioned names, to measure screening precision and recall.

### Module 3: Lend (credit memo)
- Input: a company (US public companies first, via SEC EDGAR).
- Agent task: pull financial statements, compute ratios (leverage, interest coverage, debt service coverage, liquidity, margins), factor in the rate environment, write a credit memo with a recommendation.
- Output: grounded credit memo where every figure cites its XBRL fact or source, plus a recommendation that goes to the approval queue.
- Ground truth: reported XBRL values for extraction accuracy; deterministic recomputation for ratio accuracy; memo quality via an LLM judge calibrated against the owner's own hand-graded sample.

### Parked
- A bank reconciliation agent (bank statement vs ledger matching) as a possible fourth module later. Do not start it.

## 3. Architecture overview

```
Data sources ──> Ingestion scripts ──> PostgreSQL (Neon)
                                            │
                     Rules layer (AML) ──> Alerts / Cases
                                            │
                                     Agent core (own loop)
                                            │
             ┌──────────────┬──────────────┼──────────────┐
      Model adapter    Read-only MCP     Verifiers     Corrections
      (multi-model)    tool servers    (deterministic)    memory
                                            │
                              Maker-checker review (sub-agent)
                                            │
                          Proposal ──> Human approval queue (UI)
                                            │
                              Audit log + Langfuse traces
                                            │
                       Eval runner (offline, scored, versioned)
```

Shared across modules: agent loop, model adapter, tool interface, verifier framework, approval queue, corrections memory, audit log, eval runner, web UI shell. Each module adds only: its tools, its prompts, its output schema, its verifiers, its eval dataset and metrics.

## 4. Harness design

### Agent loop
- Written from scratch. No LangChain, LangGraph, LlamaIndex or similar.
- Loop: send case context and tool definitions to the model, execute any tool calls, append results, repeat until the model returns a final structured answer or a limit is hit.
- Initial limits (tune later, keep in config): max 12 tool steps per case, a per-case token budget, a wall-clock timeout. When a limit is hit, the case is routed to human review with the partial findings, never auto-closed.

### Model adapter
- One internal interface, multiple backends: Anthropic SDK for Claude; OpenAI SDK pointed at OpenRouter (OpenAI-compatible) for DeepSeek, Qwen, Kimi, GLM and others.
- Model IDs live in config, never hard-coded.
- Every model call logs: model, provider, prompt version, input and output tokens, cost, latency.

### Tools
- Exposed as read-only MCP servers written with the MCP Python SDK.
- The agent can never write to the database, post decisions or change data. Writes happen only through the approval flow, outside the agent.
- Planned AML tools: get_alert, get_account_history, get_counterparties, get_transaction_graph (neighbourhood around an account), run_pattern_check (cycle, fan-in, fan-out, structuring detectors), screen_name (sanctions fuzzy match).
- Planned KYB tools: search_company, get_officers, get_persons_with_significant_control, get_lei_record, screen_name.
- Planned Credit tools: get_company_facts (EDGAR XBRL), get_filing_section, get_rates (FRED), compute_ratio.

### Verifiers (deterministic, run on every output)
- Schema validation with Pydantic.
- Citation check: every cited transaction, account, filing or fact ID must exist and must support the claim it is attached to (for example, a cited amount must match the stored amount).
- Arithmetic check: any number the agent states that can be recomputed is recomputed and compared.
- Module-specific checks (for example, typology must be one of the allowed values; risk rating must follow from the screening results).
- A failed verifier sends the failure back into the loop for one retry, then routes to human review.

### Maker-checker
- A preparer agent produces the output; a reviewer agent with a different prompt and checklist approves or rejects with reasons.
- Benchmark which model split works best (for example, cheap preparer plus strong reviewer, and the reverse).

### Human approval queue
- Four-eyes principle: escalations, KYB risk ratings and credit recommendations require explicit human approval in the UI.
- Every decision, approval, rejection and edit is written to an append-only audit log.

### Corrections memory
- When the owner corrects an output in the UI, the correction is stored as a structured rule or example.
- Relevant corrections are injected into the agent's context on future cases.
- The eval runner measures accuracy round over round to show whether corrections help.

### Observability
- Langfuse for traces. Trace all eval runs; sample routine runs to stay within free tier limits.
- Cost and latency per case are first-class metrics, shown in the dashboard.

## 5. Evaluation

### Principles
- Every change to prompts, tools, models or harness components is evaluated against a fixed, versioned dataset before it is accepted.
- Eval results are stored in PostgreSQL with the git commit, prompt versions and model IDs, so any two runs can be compared.

### AML metrics
- Escalation precision and recall against labels.
- False-positive reduction versus the rules-only baseline at a fixed recall.
- Typology accuracy.
- Narrative grounding rate (share of claims passing the citation check).
- Calibration: reliability diagram and expected calibration error for the confidence score.
- Cost per alert, latency per alert.

### KYB metrics
- Ownership extraction accuracy against the hand-checked set.
- Sanctions screening precision and recall on seeded name variants.
- Risk rating agreement with the owner's labels.

### Credit metrics
- Extraction accuracy against reported XBRL values.
- Ratio accuracy (deterministic recomputation).
- Memo grounding rate.
- Memo quality from an LLM judge, with the judge's agreement against the owner's hand grades reported alongside.

### Ablations (run for each module)
Remove one component at a time and measure the change: verifiers, maker-checker review, specific tools (for example the graph tool), corrections memory, rules-layer hints. Report results in a table in docs/results.md.

### Model benchmark
Run the same eval set across Claude and the open-weight models. Report accuracy, cost per case and latency side by side. Include at least one open-weight model served by a US or EU-hosted provider to show which models could plausibly run inside a bank.

### Regression
- A small fast eval subset runs in CI on every push.
- The full eval runs nightly via GitHub Actions and on demand.

## 6. Data sources and integrations

All free. Register for keys where needed and store them only as secrets.

| Source | Used for | Notes |
|---|---|---|
| IBM synthetic AML dataset (Kaggle) | AML transactions and labels | Raw files are too large for free hosting; slice in Kaggle Notebooks (see below). |
| OpenSanctions bulk data | Sanctions and PEP screening | Licensed CC BY-NC for non-commercial use. Use bulk downloads loaded into Postgres (or self-hosted yente), not their hosted API. |
| OFAC SDN list, UK sanctions list | Sanctions screening | Free government downloads. |
| UK Companies House API | KYB: companies, officers, persons with significant control | Free API key with registration. Respect rate limits. |
| GLEIF LEI API | Legal entity identifiers and parent relationships | Free, no key. |
| SEC EDGAR APIs | Credit: XBRL company facts and filings | Free, no key. Send a descriptive User-Agent with contact email per SEC fair access rules and stay under their rate limit. |
| FRED API | Interest rates and macro data | Free API key. |
| Plaid Sandbox | Optional: small-business cash flow for Credit | Free sandbox only. |

### IBM dataset slicing rules
- Do the slicing in a Kaggle Notebook with Polars or DuckDB; upload only the slice.
- Preserve complete laundering patterns: keep every account and transaction belonging to each labeled pattern included.
- Include enough normal traffic around those accounts to produce a realistic false-positive rate.
- Keep the slice within free database limits. Record the slicing logic and random seed in data/README.md so the slice is reproducible.

### AML rules layer
Deterministic detectors that generate alerts before the agent runs: rapid fan-out, fan-in, cycles, structuring just under reporting thresholds, sudden volume spikes. Tune them to over-alert slightly, as real systems do. The rules-only results are the baseline the agent must beat.

## 7. Models and cost

- One aggregator key (OpenRouter) for all non-Claude models; Claude via OpenRouter or the Anthropic API directly.
- Use free models during development. Free model availability and limits change often; never depend on one specific free model.
- Use a small prepaid balance for real benchmark runs; prepaid credit prevents overspending. Set spend caps where providers allow.
- Chinese model APIs only ever receive synthetic or public data.
- Use prompt caching where supported, short schema-constrained outputs, and cheaper models for routine steps.

## 10. Environment and hosting

### Development
- Development happens only in GitHub Codespaces on the owner's personal GitHub account. Nothing is installed locally.
- Use the 2-core machine, a short idle timeout, and a spending limit of zero. Stop the codespace when not in use.
- Heavy data work happens in Kaggle Notebooks, not in Codespaces.
- Claude Code runs in the Codespaces terminal, using a personal Claude account or API key.

### Hosting
- Frontend: Vercel (free tier), auto-deploy from GitHub.
- Backend: Render free web service, auto-deploy from GitHub. It sleeps when idle, so the UI must handle a cold start gracefully. Agent jobs run in-process from the API; there is no separate background worker on the free tier. Large batch eval runs go through GitHub Actions instead.
- Database: Neon, with separate dev and prod branches.

### Public demo
- Replay mode for visitors: browse recorded cases, traces, eval results and benchmarks.
- Only the owner (via Auth.js) can trigger live agent runs, so visitors cannot spend API credit.

## 11. Security and boundaries

- Personal accounts and billing only. No client code, client data or work accounts anywhere in this project.

## 14. Key decisions and rationale

- AML first, because labeled ground truth makes the eval harness verifiable before tackling fuzzier modules.
- Own agent loop instead of a framework or the Claude Agent SDK, because learning the harness is a goal and the system must stay model-agnostic for benchmarking.
- Read-only agent with a separate approval flow, mirroring maker-checker and segregation of duties in real banks.
- Deterministic verifiers before LLM judges, because objective checks are cheaper, more reliable and easier to defend.
- OpenRouter as a single model gateway, so switching models is a config change and billing is one account.
- Cloud-only development, because the owner's work laptop only permits Python in a venv and the project must stay separate from work.
